# Architecture

## Data model (PostgreSQL / Supabase)

| Table | Purpose | Notes |
|---|---|---|
| `admins` | Who may administer | Managed with SQL only; no API access |
| `business_settings` | Single row (`id = 1`) of editable business info | Public read, admin update. Highlights and how-to-buy steps are JSON arrays |
| `faqs`, `testimonials` | Owner-written content | Public sees `is_published` rows only |
| `products` | PCs | `numeric(12,3)` price (TND has millimes), `status` enum, `is_archived` soft delete, unique `slug` |
| `product_images` | Photos | One primary per product (partial unique index), ordered by `position` |
| `product_status_history` | Audit of status changes | Written by a trigger |
| `sales` | Manual sales ledger | `ON DELETE RESTRICT` to products; snapshots product name and listed price; `is_voided` keeps history; one active sale per product (partial unique index) |
| `inquiries` | Leads from the contact form and chat escalations | `source` = `form` / `chat`; status pipeline new → contacted → negotiating → converted / closed |
| `contact_events` | WhatsApp / Messenger / phone / chat button clicks | Clicks only, not messages |
| `conversations`, `messages` | Website chat | Visitor access by token hash; admin access by RLS; in the Realtime publication |

Customers are stored as snapshots on `sales` and `inquiries` rather than in a separate `customers` table: the business model is direct contact and a separate customer registry would duplicate data without a use case yet.

## Decisions

1. **No service-role key.** Public writes use `SECURITY DEFINER` functions with validation and rate limits inside; admin writes run as the signed-in admin and are gated by RLS. A leaked deployment therefore cannot bypass RLS.
2. **Status integrity in the database.** A trigger rejects any status change not made by `set_product_status` / `record_sale` / `void_sale` (they set a transaction-local flag), so "sold" always has a sale row.
3. **Public pages use an anonymous client** (no cookies), so a logged-in admin sees the site exactly as visitors do (archived products stay hidden).
4. **Deterministic chatbot** (`src/lib/chatbot/engine.ts`): a pure function over database data, unit-tested for "never invents". `FallbackResponder` is the optional AI hook.
5. **Direct-to-Storage uploads** from the admin's browser (policy: admins only), then a server action verifies the real file signature and registers the image.
6. **Dynamic rendering for database pages.** They render per request, so builds and CI need no database or secrets.
7. **Image paths are generated by the app** (`products/<id>/<uuid>.<ext>`), and `registerImageAction` rejects any other path.

## Request flow: chat

```
Visitor browser ──POST /api/chat──▶ Next.js route
   httpOnly cookie token              ├─ rpc chat_start (first message): creates conversation, returns token
                                      ├─ rpc chat_post_visitor_message
                                      ├─ if not escalated: respond() over catalog+FAQ+settings → rpc chat_post_bot_message
                                      └─ rpc chat_get_messages → new messages
Admin inbox (browser) ◀── Supabase Realtime (RLS: admins only) ──▶ reply = INSERT messages(sender='admin')
Visitor polls GET /api/chat?after=<id> every 6 s while the window is open
```

## Visual design system

Tokens live in `src/app/globals.css` (`:root` variables, mapped to Tailwind colours such as `bg-brand`, `text-accent`).

- **Idea:** the shop's own vernacular, a BIOS / CPU-Z readout. Specs are `label ........ value` rows (`.leader`), values in Martian Mono; everything else is Instrument Sans; headings are Big Shoulders.
- **Colour:** steel-graphite chassis (`--bg`), one flat **BIOS blue** (`--brand`) used only for the hero and the closing contact band, **signal amber** (`--accent`) for prices and actions.
- **The one memorable element:** the hero's live stock readout (`StockReadout`), built from real database counts. It prints in line by line once (`.post-line`); reduced-motion disables it.
- **Rules to keep it distinctive:** no boxes around every section (use rules and open lists), no all-caps eyebrow labels, mono only for data, one motion moment, blue never used as a body background.
- Change the whole palette by editing the variables in `:root`; admin screens use the same tokens.
